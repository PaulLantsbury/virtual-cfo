# Provider test writer preparation — 9 October 2026

Prepared locally, not activated. No API requests, credentials, schedule, source transactions or database changes are performed by these files.

`provider-write-plan.mjs` prepares one bounded zero-tax/no-shipping Shopify test order and a Xero non-stock service invoice. Discount/tax/shipping Shopify scenarios and refunds fail closed until separately verified adapters exist; the existing 10-order/four-refund daily plan cannot yet be executed by this adapter. The Shopify request contains no customer, contact details, product variant, transaction or fulfilment; both receipt flags are false and inventory is BYPASS. Test orders remain excluded from eligible merchant revenue. Do not turn `test` off to populate dashboards.

Xero uses an existing selected synthetic contact and mapped account, GBP and NoTax. DRAFT is the default and does not exercise posted P&L; An optional posted demo mode is separately gated: `financialMode=posted_demo_only` in the private config and `NIGHT_SCOUT_TEST_WRITER_POSTED_DEMO_APPROVED=true` at action time, plus fresh provider proof of exact connected GBP demo tenant. Default drafts prove transport; authorised demo invoices book GBP10 revenue and GBP10 receivables per action, at most GBP60 each over six actions, with no VAT, stock, payment or invoice email. This is prepared only, not activated. No payments, invoice emails, contacts, stock items or bank transactions are created. Exact tenant identity and appropriate granular `accounting.invoices` consent are required; do not extend the current read-only collector credential automatically.

The executor requires a durable atomic ledger adapter and an exact verified staging target, bounded dates and cap. It records submitted before a provider call. Unknown outcomes return a safe stop result and retain the claim; subsequent attempts demand reconciliation rather than resubmission. `provider-pg-ledger.mjs` implements programme-row locked atomic caps, immutable state transitions, payload conflict checks and global stop after an uncertain write. The ledger SQL remains a proposal without writer role/grants. Target-bound reconciliation is an operator gate; it never resets claims or blindly resends. No process-local ledger is acceptable.

`provider-transport.mjs` supplies fixed Shopify 2026-07 GraphQL and Xero invoice endpoints with redirects disabled, a 10-second timeout spanning the response read, 128KB streamed response cap and fixed safe errors. Shopify must report `partnerDevelopment=true`, exact domain and GBP. Xero must show the exact connected tenant and `IsDemoCompany=true`, GBP. No caller assertion alone substitutes for provider checks.

Example start 12 October 2026, hard stop 26 October; explicit dates required, no automatic renewal or backdated catch-up. Shopify cash charged is zero; each order nominally GBP60, excluded from eligible revenue. Xero drafts nominally GBP10 each, excluded from posted P&L; the separately gated posted demo mode can exercise booked revenue after read refresh. Each provider needs its own exact config/programme row and credential. No scheduler has been created. Shopify now mints a fresh short-lived writer token each due run using the same-organisation client-credentials grant at the exact shop, with bounded replies and authoritative access-scope verification: read_orders/write_orders only, optional read_all_orders, no other write scope. Unattended Xero refresh is implemented by `xero-writer-refresh.mjs`: it reuses the existing staging AES-256-GCM envelope boundary and OAuth refresh parser while keeping a new, isolated `writer_envelopes` table. It never reads or rotates the existing read-worker credential. A permanent atomic refresh claim prevents parallel or interrupted refresh replay. New refresh material is encrypted and stored with exact tenant/version/claim before scope validation or provider use. Unknown refresh/rotation outcomes stop the programme and retain the claim for operator reconciliation; there is no lease expiration or automatic reset. Scoped private configuration is `NIGHT_SCOUT_TEST_WRITER_ENVELOPE_MASTER_KEY`, `NIGHT_SCOUT_TEST_WRITER_ENVELOPE_KEY_VERSION`, `NIGHT_SCOUT_TEST_WRITER_XERO_CLIENT_ID`, `NIGHT_SCOUT_TEST_WRITER_XERO_CLIENT_SECRET`. Writer consent requires `offline_access accounting.invoices accounting.settings.read`; optional `accounting.contacts.read` supports selecting the existing synthetic contact. Legacy broad transaction permissions and extra write scopes are rejected. Separate consent/bootstrap envelope seeding is still required before activation, no plaintext refresh token environment or file.

`provider-access-proposal.sql` adds an isolated NOLOGIN/NOINHERIT `night_scout_test_writer_service` capability role, RLS on all new tables and narrowly scoped SECURITY DEFINER RPCs with fixed search paths. It grants execution only, never direct credential/table reads or raw updates. Posted and draft payloads are independently validated at the transport boundary with exact allowlisted shapes; forged plans cannot add payments, emails, stock variants/items, contact mutation or additional invoices. An operator must create the dedicated restricted NOINHERIT login with connection limit 1–3 and membership without other privileges: service membership must have ADMIN false, INHERIT false and SET true. Runtime inspects actual session login, both roles and all memberships before any credential RPC, rejecting elevated flags or extra memberships. `provider-rpc-ledger.mjs` is the CLI ledger; the direct PostgreSQL adapter remains a disposable contract reference. Every CLI RPC transaction selects the capability role locally, including after pool reconnection. No existing roles, Xero reader envelope, finance tables or collection privileges are altered.
