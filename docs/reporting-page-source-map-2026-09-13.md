## Shared read paths and scope differences

1. **Evidence-based sales path:** `src/lib/analytics/useVerifiedBriefing.ts` → `useStoreReporting` → `stores(id,currency_code,timezone)` with exact active-store match. `storeReporting.ts` validates currency precision/timezone and derives store-local completed week/month. React Query keys include store, currency, timezone and period. `experiments/financial-v1/rpc-sales-adapter.mjs::fetchVerifiedSales` calls `verified_sales_source`, rejects returned store/period/version/coverage mismatches and delegates to `cloud-sales-adapter.mjs::calculateMappedSales`. The repository SQL (`db-migrations/proposed/finance_v1_member_read.sql`, duplicated in staging setup) reads `finance_v1.coverage_evidence`, `order_mapping`, `refund_mapping` backed by evidence, with membership checking. It returns store rows for the adapter to select event periods; endpoint name alone does not certify completeness.
2. **Legacy period path:** `src/lib/analytics/useLatestDataPeriod.ts` → `reportingPeriod.ts::resolveReportingPeriod` probes `order_count` until an order-containing completed period is found (up to24 months/104 weeks). Calendar dates use the **browser timezone**, unlike the briefing. Zero-order refund-only periods can be skipped. It then calls `phase1Metrics.ts::getPhase1Metrics`: `gross_revenue`, `net_sales`, `average_order_value`, `repeat_purchase_rate`, `discount_dependency`, `refund_rate`, `contribution_margin_pct`, and `recoverable_contribution_range`. First seven receive store/date; recoverable range receives **store only**. No currency is part of this RPC contract. Loader errors suppress the whole returned metric panel; finite zeros can display, but correctness of legacy definitions remains unverified.
3. **Legacy table semantics:** recovered `db-migrations/reconciliation/2026-09-08/recovered/20260429000001_phase1_metric_functions.sql` uses legacy `orders` and created-at dates, including denominator/refund-status treatment that conflicts with agreed event-based rules. This is code evidence, not proof current live functions exactly match that snapshot. Do not certify or use these values interchangeably with `finance_v1` sales.
4. **Marketing path:** page-local `readMarketingSource` keeps nullable values instead of old adapter coercions. Requested dates are distinct from returned snapshot periods; currency is not certified, so monetary source readings avoid guessed GBP. `db-migrations/migrations/20260507000002_marketing_intelligence_schema.sql` defines channel/blended snapshot RPCs. Older `src/lib/analytics/marketingChannelMetrics.ts::getMarketingChannelMetrics` also loads `channel_opportunities_active`/trend information and includes legacy numeric coercions; it is not the page's current reader. Its existence is not an implemented shared authoritative model.
5. **Fixture paths:** `src/lib/data/{business-snapshot,cash-snapshot,channel-metrics,growth-metrics,pricing-metrics}.ts`, `src/lib/mock-data.ts`, and page-local arrays are business examples, not database storage. `scenario-model.ts::SCENARIO_BASELINE_INPUTS` is internally coherent but also fixed input data. Sharing constants does not make values authoritative. `src/lib/metrics.ts` names metrics but does not unify their actual calculation paths.

## Duplicates and remaining gaps

- Five pages call the same legacy eight-metric bundle even when they need one/two values or only a period label; visits repeat work and unrelated RPC failure suppresses otherwise useful readings. The briefing already has a distinct cache-aware evidence path.
- Global timeline selection does not guarantee matching dates: briefing respects store timezone and requested period; legacy pages walk back by order count. Sample periods remain independent even when adjacent source labels change.
- Two financial systems coexist: legacy order/snapshot aggregates and evidence-based `finance_v1` mapped events. A “single database” alone will not reconcile these competing definitions.
- Multiple independent sample profit, contribution, recovery and cash formulas remain across margin/pricing/marketing/cash/opportunities. Profit Overview and Scenario Planner are aligned with each other only; their chosen95k sample does not certify other pages.
- Review UI (`src/pages/financial-review.tsx`) and the verified-sales page are outside the ten main screens but must retain their source/coverage distinction during migration. Data availability, source validity, period completeness and financial approval are separate states.
