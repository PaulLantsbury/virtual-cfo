Later refunds belong to actual refund dates and retain earlier originals plus earlier refund history needed to enforce cumulative revenue/tax/COGS caps. Sum monthly pence to annual oracles; combined per-order ratios use summed amounts divided by summed original orders, never an average of daily ratios.
- Mutating an original date, currency, source amount, cost, recovered stock or earlier refund must invalidate every affected dependency period. Unrelated later append stability must be demonstrated against the installed versioned contract, including installed triggers; a pure proposal hash does not prove it.

## Recovery and daily failure rules

A failed or uncertain run must not erase prior good data, clear reservations, delete seals or manufacture a fresh timestamp. Stage the new source version and complete verification before changing the selected reporting version. Log a durable run identity, requested London dates, profile/start, source digest, attempted mutation set and final outcome in private receipts. Concurrent runs must claim the same scope once; exact replay inserts nothing, changed immutable IDs fail.

On confirmed rollback, keep the last accepted selected version and its original source date. On uncertain commit, inspect canonical rows, coverage, invalidation history and run receipt before deciding whether an exact replay is safe. Existing v1 triggers may have invalidated coverage even when monetary amounts look unchanged: retain a visibly dated snapshot only if its reader contract permits it, otherwise show unavailable until review. Never restore freshness by copying observed/fetch/insertion timestamps into source-as-of.

Historical corrections produce a new evidence/snapshot version plus append-only invalidation/supersession history. Restore a prior selected version only when its sources still validate; rollback is not permission to delete newly observed financial events. Non-actionable failed refreshes should not generate invented owner alerts; the product may show a truthful freshness limitation.
