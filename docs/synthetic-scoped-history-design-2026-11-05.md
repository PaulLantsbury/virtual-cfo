# Scoped history design rehearsal

Status: offline product/architecture proposal. No application reader, sealed evidence, database, access or schedule has changed.

Current profit source revisions hash the store's complete retained order/refund history. Existing source-change triggers also invalidate coverage for the whole store. Adding a later trading day can therefore invalidate an otherwise unchanged closed month. A daily generator must not bypass those protections, reuse a stale seal or keep labelling old evidence current.

The proposed next version binds each complete monthly result to an explicit coverage version and its dependency closure: selected original orders, selected refunds and their actual earlier originals, earlier refund history needed to enforce original-order component caps, and the selected month's cost/expense sources. Business, currency, timezone, profile, period and formula contract remain part of the revision. Subsequent refunds retain their own event dates and do not revise the original month's AOV. Corrections to an original source still invalidate every dependent period.

The new pure local `scoped-history-proposal.mjs` rehearses that closure without changing the financial engines. Five tests pass: later-day append preserves the unchanged closed month, while same-month financial/payroll changes and earlier linked original changes invalidate it; a later refund changes its own period; missing original evidence, incorrect scope or missing review fail closed. Existing canonical sales/profit calculations return the same January amounts before and after later-month append, including £1,976.02 operating profit.

This is insufficient to operate daily. The existing store-wide reader and triggers remain authoritative. Before implementing a scoped reader, specify and test a complete source-event mutation impact graph, independent period coverage attestations, append receipts, concurrent replay/uncertain outcomes and immutable replacement versions. Date/currency/timezone changes require invalidating all affected periods. Historic line-cost and stock-recovery corrections require their own cross-period dependency edges. A complete source-version/closure proof must retain raw monetary precision and source evidence; caller-provided manifests alone do not certify completeness.

Prepare a versioned adapter/schema proposal and rehearse it against the actual installed trigger contract, including unrelated-store preservation and historical correction cases. Never weaken or disable current invalidation globally to make daily updates appear healthy. Closed snapshots should remain visibly dated and explicitly selected; replacing them requires a new reviewed version. Provider ingestion acceptance, cash/customer/channel coverage and hosted release remain separate workstreams.
