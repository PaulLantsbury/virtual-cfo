# Durable PKCE context encryption component

Prepared, default off and disconnected. `durable-pkce-context.mjs` performs server-only AES-256-GCM encryption of a strict OAuth context. It makes no provider calls, SQL changes, persistence or HTTP routes. It is **not** the adapter's full `proofs` implementation and does not activate customer reconnect.

Configure `createDurablePkceContext` from trusted server code with `enabled: true`, the exported `DURABLE_PKCE_KEY_PURPOSE`, an active key ID and a Map of at most eight independently generated 32-byte keys. Never use the refresh-envelope master key here. The purpose declaration separates authenticated encryption domains; software cannot prove operators supplied different key bytes. Keep these keys in a dedicated secret/configuration namespace. Encrypt with the active key, retain old keys only as needed to read unexpired capsules, then remove them. Key version is authenticated in AAD. Caller-owned key buffers are copied.

`seal({phase, binding, pkceVerifier, expiresAt})` returns an opaque ciphertext. Both `authorization` and `exchanging` require store, owner, authenticated server session digest, attempt, state digest, pinned tenant, connection and current credential version. `exchanging` additionally requires the exclusive database exchange claim. UUIDs/digests and strict schema are validated. A PKCE verifier is 43–128 RFC 7636 unreserved characters. Use a cryptographically random verifier; this component validates syntax, not source entropy. Generate it only on the server.

`open(capsule, {phase, binding})` returns a frozen server-private record including the secret verifier. Obtain expected bindings from authenticated session and saved attempt, never unsigned browser claims. Returned state must first be hashed and compared with saved `stateDigest` by the future callback boundary. No authorization code is accepted or logged here. Generic exceptions contain no verifier or supplied payload.

Time comes exclusively from the server's real clock. Seal expiry must be future and at most ten minutes away. Open rejects expired, future-issued or over-ten-minute payloads. The caller must use the SQL attempt's original expiry when sealing; switching to the exchange phase MUST retain the original expiry, not extend the consent window. This crypto component cannot independently query the attempt. SQL still checks saved expiry, membership, lease and one-use claim.

The future proof provider must combine this with authenticated server sessions, pending/start issuance before the SQL begin step, durable encrypted storage, exact saved-attempt lookup, constant-time returned-state verification, exclusive claim before one provider exchange, scope/tenant validation, and the existing refresh-envelope issuer. The current adapter's `begin` returns only public pending ID/expiry and does not expose all server binding fields: integration must explicitly design a private saved-attempt lookup rather than trust browser-provided tenant/version fields. Failure/final grant proof issuance and replay protection remain separate work. Do not mount a route based only on this module.

Run `node --test experiments/xero/durable-pkce-context.test.mjs`. Nine focused checks exercise real GCM mutation, wrong purpose and bindings, strict decrypted schema, expiry, rotation, phase claim and key-buffer isolation. They are not live OAuth, persistence, DB concurrency or customer-readiness acceptance.
