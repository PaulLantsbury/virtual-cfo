## What “connected” means

A number is connected when its business inputs come from validated records for the selected company and period. It can be computed in SQL, the reporting server, or the browser. **A browser-calculated ratio, bridge, per-order amount or scenario does not need a separate database column merely to be connected.** What matters is the provenance of its inputs, its formula and its label.

**User assumptions do not need a database link.** A DB-backed baseline combined with a clearly labelled user target, budget change or sensitivity is a legitimate conditional calculation. The current sample mixed outputs remain unsupported as company results because their baseline/customer inputs are fixtures—not because they are computed in the browser or include an assumption.

**Existing reviewed monthly financial inputs are already available.** The sample multi-month/time-series, historical comparison, weighted trajectory and response functions do not currently consume those records. This is an input/period-wiring gap, not a requirement to save a separate result for every cell.

The current default monthly view is connected to verified financial inputs. The separately chosen sample review still uses `DAILY_SAMPLE`. Its acquisition/customer facts and response assumptions are not made real by placing Supabase financial totals elsewhere on the page. Nothing in this audit treats an editable target or hypothetical response as an observed fact.

## Database, server and browser responsibilities

| Layer | Current responsibility | What it does not establish |
| --- | --- | --- |
| Supabase history records | Financial events/orders/refunds/lines/returns, classified cost inputs, exact coverage, monthly seals/versions and membership-scoped source evidence. | Customer acquisition eligibility, mature cohorts, campaign response or cash affordability are not supplied by the current Marketing financial response. |
| Restricted reporting server | Authenticates membership and exact requested month/version; reads source records, journals and sealed versions, verifies canonical source revisions and recomputes core sales/cost/profit totals on read; returns reconciled evidence through `/api/history-reporting/months` and `/api/history-reporting`. Route module delegates financial reads to the history service. | It does not run the static Marketing sample or turn its fixture assumptions into measured company inputs. |
| Browser validation/composition | `useReviewedHistory`, `historySupportedInput`, `composeHistoryMonth`, `adaptSupportedReporting` verify response scope/metadata and independently reconcile financial arithmetic. Missing/failed/withdrawn/cross-store data remains unavailable. | A valid financial month is not sufficient evidence for CAC, channels or a forecast. |
| Browser Marketing calculations | `linkedMarketingMetrics` computes connected POAS/ROAS, overheads excluding D&A and per-order displays; shared financial composition supplies reconciled subtotals. | Computation location is not an unlinked-input warning. These derived outputs need no additional stored result columns. |
| Explicit sample planner | `buildMarketingReview`, `requirements`, `spendScenario`, `scenarioBridge`, `DecisionProfitBridge` calculate illustrative historical/forward amounts from static fixtures and editable assumptions. | These are not the currently selected company’s database results. They remain sample/mixed until the relevant input path is replaced. |

Location shorthand: **C** = `components/NewMarketingLive.tsx` and `lib/marketing/linked-model.ts`; **H/T/B/S** = `pages/marketing-efficiency.tsx`, `lib/marketing/review-model.ts` and, for the bridge, `components/DecisionProfitBridge.tsx`. Model function names are shown in each row so this survives line-number changes.

Needed-input shorthand: **F** = verified matched financial inputs; **A** = eligible acquisition spend matched to evidenced first-time customer identities; **I** = first-order revenue/cost/contribution facts matched to those acquired customers. These are inputs/contracts—not requests to persist every derived answer.

## What remains unsupported and why

- The connected CAC output is unavailable because financial advertising totals do not specify eligible acquisition spend or identified first-time customers. Existing orders alone must not be converted to new customers by the fixture’s 39%/43% share.
- First-order contribution/revenue and mature payback need matched customer/cohort observation, not all-order averages multiplied by 94%/98%. Mature payback, cohort and channel attribution in the default gap notice are capability/status statements; no numerical result is currently produced there.
- The sample’s financial inputs are static even where equivalent monthly financial facts already exist in Supabase. Replacing those inputs is a wiring task; it does not require storing every POAS, target gap or bridge result.
- A real baseline plus user response sensitivity can support a **conditional scenario**, accurately labelled “DB-backed baseline + user assumptions”. It still cannot be called observed future EBITDA, measured CAC response, statistical confidence or cash affordability.
- Current default Marketing supports one reviewed month and version. Multi-month, weekly, prior-year, rolling and response-chart wiring is not completed merely by this audit. Finer periods need honest source coverage; monthly seals must not be divided into invented daily/weekly observations.
- Draft activity, reviewer and date fields remain temporary browser inputs. No action, advertisement change or reminder is saved or scheduled. The sample New Plan link carries sample review context, not a verified financial baseline.

## Safest next implementation sequence

1. Reuse the exact scoped, validated financial inputs already available for every financially supported Marketing calculation. Preserve one clear source context and denominator across cards, coverage, charts, narrative and evidence.
2. Where complete comparison/bucket inputs exist, use the same pure formulas to compute historical ratios and thresholds in the browser or server. Do not add redundant database columns for these answers.
3. Define and add the missing acquisition and first-order evidence inputs with explicit eligibility, identity/unknown handling, dates and cost matching. Validate against independent known-answer examples before enabling CAC or customer economics.
4. Rebase the 30-day model on accepted inputs, label its rate extrapolation and editable assumptions, and keep cash/stock/capacity checks separate. Persist input choices only if saved scenarios are required.
5. Replace yellow sample provenance only for output families whose actual input wiring and source checks are completed. Continue highlighting unsupported facts and hypothetical assumptions with text as well as colour.
